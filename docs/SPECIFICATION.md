## 1. Роль Codex и правила выполнения

Ты — **Senior Android Engineer / Tech Lead** с опытом коммерческой разработки Android-приложений, проектирования offline-first систем, обеспечения безопасности персональных данных, тестирования и публикации приложений. Работай как ответственный инженер, а не как генератор демонстрационного кода.

Дополнительно выполняй функции:
- **Product Engineer:** уточняй неоднозначные продуктовые решения, но не блокируй разработку из-за несущественных вопросов; документируй разумные предположения.
- **Android Architect:** поддерживай понятные границы слоёв, тестируемость и минимальную сложность.
- **UX/UI Engineer:** делай удобный интерфейс для мастера, который пользуется телефоном одной рукой между клиентами.
- **QA Engineer:** создавай автоматические тесты и проверяй пограничные сценарии.
- **Security/Privacy Engineer:** минимизируй сбор данных и доступ к контактам.
- **Release Engineer:** обеспечь воспроизводимую сборку, инструкции и выпуск APK/AAB.

### Обязательные правила
1. Создавай **реально запускаемое Android-приложение**, а не статический макет, псевдокод или набор экранов без работающих сценариев.
2. Прежде чем менять существующий репозиторий, изучи структуру, README, Gradle-конфигурацию и тесты. Не удаляй пользовательский код без необходимости.
3. Не выдумывай результаты сборки, тестов или проверки на устройстве. Если среда не позволяет выполнить шаг — прямо укажи ограничение.
4. Работай **вертикальными срезами**: схема БД → репозиторий → бизнес-логика → UI → тесты.
5. После каждого этапа предоставляй краткий отчёт: что сделано, какие файлы изменены, какие команды выполнены, что прошло/не прошло, что осталось.
6. Не добавляй ненужные SDK, аналитику, рекламные трекеры, облачные сервисы или авторизацию.
7. Все данные должны сохраняться после закрытия и повторного открытия приложения; не хранить рабочие данные исключительно в памяти UI.
8. Выбирай стабильные совместимые версии библиотек, доступные на момент реализации; фиксируй их в version catalog. Не придумывай номера версий.
9. Обеспечь доступность, обработку ошибок, валидацию и корректную работу без интернета.
10. Если решение влияет на риск потери данных, приватность, оплату или публикацию, сначала объясни выбор и получи подтверждение.

## 2. Цель продукта

Разработать персональный **ежедневник для парикмахера на Android**, позволяющий быстро вести расписание приёма клиентов, добавлять клиентов вручную или выбирать из телефонных контактов, назначать услуги, время и длительность, видеть свободные интервалы и историю посещений.

**Главный пользователь:** один парикмахер/мастер, который самостоятельно управляет своим графиком на одном Android-устройстве.

**Ключевой результат MVP:** мастер за 20–30 секунд может открыть приложение, выбрать день, найти/добавить клиента и записать его на свободное время; запись остаётся доступной офлайн после перезапуска.

### Не входит в MVP
- Регистрация, аккаунты, многопользовательская работа и синхронизация между устройствами.
- Онлайн-запись клиентов и публичная страница бронирования.
- Приём платежей, эквайринг, кассовая интеграция.
- SMS/WhatsApp/Telegram-рассылки от имени мастера.
- Автоматическое облачное резервное копирование.
- Интеграция с Google Calendar.
- Складской учёт, зарплаты сотрудников и полноценная CRM.

Архитектура должна позволять добавить эти возможности позже без переписывания основного доменного слоя.

## 3. Технологический стек

**Приоритет: нативный Android.**

| Область | Решение |
|---|---|
| Язык | Kotlin |
| UI | Jetpack Compose + Material 3 |
| Архитектура | MVVM + UDF (однонаправленный поток данных), Repository |
| Асинхронность | Kotlin Coroutines, Flow/StateFlow |
| Локальная БД | Room (SQLite), миграции |
| DI | Hilt, если не создаёт неоправданную сложность; иначе простой DI с объяснением |
| Настройки | Jetpack DataStore |
| Навигация | Navigation Compose |
| Даты и время | `java.time`, корректная работа с часовым поясом |
| Фоновые задачи | WorkManager для подходящих отложенных задач |
| Уведомления | NotificationManager, каналы уведомлений, runtime permission на Android 13+ |
| Тестирование | JUnit, kotlinx-coroutines-test, Room tests, Compose UI tests |
| Сборка | Gradle Kotlin DSL, Version Catalog |
| Минимальная версия Android | minSdk 26 (Android 8.0), если нет технической причины изменить |
| Target/Compile SDK | актуальные стабильные версии, совместимые с инструментами и требованиями Google Play на момент сборки |

**Важно:** не подключать `READ_CONTACTS` для простого выбора человека из телефонной книги. Использовать системный выбор контакта через `ActivityResultContracts.PickContact` или эквивалентный безопасный системный picker; получить только разрешённые выбранным пользователем данные по выданному URI. Если для конкретного способа чтения телефона потребуется дополнительное разрешение — объяснить причину и по возможности выбрать вариант без широкого доступа. Проверить работу на реальных версиях Android.

## 4. Функциональные требования

### 4.1. Главный экран: расписание

**FR-001.** При открытии приложения показывать расписание на текущий локальный день.

**FR-002.** Отображать выбранную дату, день недели и быстрый переход «Сегодня».

**FR-003.** Переключать даты стрелками и календарным выбором даты; предусмотреть переход к виду «Неделя» и «Месяц» (минимум: дневной список + месячный выбор даты для MVP).

**FR-004.** Показывать записи в хронологическом порядке: время начала, время окончания, имя клиента, услуга, статус, стоимость (если задана).

**FR-005.** Предусмотреть пустое состояние «На этот день записей нет» с действием «Добавить запись».

**FR-006.** Нажатие на запись открывает детали с возможностью изменения, завершения, отмены и удаления.

**FR-007.** Кнопка «+ Запись» должна быть доступна с главного экрана; выбранная дата автоматически подставляется в форму.

**FR-008.** Отображать визуально различимые статусы записей и занятость времени. Цвет не должен быть единственным способом передачи статуса.

**FR-009.** Если записей много, список должен корректно прокручиваться без наложений и пропусков.

**FR-010.** После изменения записи расписание обновляется без перезапуска приложения.

### 4.2. Клиенты

**FR-011.** Экран «Клиенты»: поиск по имени и номеру телефона, список в алфавитном порядке.

**FR-012.** Создание клиента вручную: имя (обязательно), телефон (необязательно), заметка (необязательно).

**FR-013.** Возможность выбрать контакт из телефонной книги через системный picker; заполнить доступные имя и номер, показать предварительный просмотр и позволить отредактировать перед сохранением.

**FR-014.** Если у контакта несколько номеров, предложить выбрать один; если номер недоступен — разрешить сохранить имя без номера.

**FR-015.** При отказе/отмене выбора контакта приложение не должно падать; ручное добавление остаётся доступным.

**FR-016.** Проверять возможные дубликаты по нормализованному телефону и предлагать открыть существующего клиента или сохранить нового. **Не объединять автоматически.** Клиенты с одинаковыми именами допустимы.

**FR-017.** Карточка клиента: имя, телефон, заметка, количество посещений, история записей (прошедших и будущих), кнопка «Записать».

**FR-018.** Редактирование клиента должно сохранять связь с существующими записями.

**FR-019.** Удаление клиента с историей требует явного подтверждения. В MVP предпочтительна архивация клиента, чтобы не потерять историю. Архивные клиенты не показываются в обычном списке, но остаются в исторических записях.

**FR-020.** По номеру телефона доступно действие «Позвонить» через `ACTION_DIAL` (без разрешения на прямой звонок).

### 4.3. Услуги

**FR-021.** Экран «Услуги» с созданием, редактированием и архивацией услуг.

**FR-022.** Поля услуги: название (обязательно), длительность в минутах (обязательно, положительная), цена (необязательно, неотрицательная), заметка (необязательно).

**FR-023.** При первом запуске предложить стартовые услуги (редактируемые): мужская стрижка 30 мин, женская стрижка 60 мин, детская стрижка 30 мин, окрашивание 120 мин, укладка 45 мин. **Не назначать выдуманные цены.**

**FR-024.** Архивация услуги не должна менять исторические записи.

**FR-025.** При выборе услуги в форме записи автоматически заполнять длительность и стоимость, но разрешать изменять их для конкретного визита.

### 4.4. Запись клиента

**FR-026.** Поля записи: клиент (обязательно), услуга (обязательно), дата (обязательно), время начала (обязательно), длительность (обязательно), стоимость (необязательно), заметка (необязательно), статус.

**FR-027.** Время окончания вычислять из начала и длительности. Длительность хранить в минутах.

**FR-028.** В форме записи можно выбрать существующего клиента или создать нового, не теряя уже введённые дату/время/услугу.

**FR-029.** Нельзя сохранять некорректную дату, нулевую/отрицательную длительность, пустого клиента или пустую услугу.

**FR-030.** Проверять пересечения с активными записями по правилу полуоткрытых интервалов: `[start, end)`. Записи 10:00–11:00 и 11:00–12:00 не конфликтуют.

**FR-031.** При пересечении показывать предупреждение с конфликтующими записями и предложением выбрать другое время. **По умолчанию запрещать сохранение конфликтующей активной записи**; отменённые записи не блокируют слот. Проверку делать и на уровне бизнес-логики в транзакции, не только в UI.

**FR-032.** При изменении записи исключать её саму из проверки конфликтов.

**FR-033.** Поддерживать статусы: `PLANNED` (запланирована), `COMPLETED` (выполнена), `CANCELLED` (отменена), `NO_SHOW` (клиент не пришёл). Только `PLANNED` блокирует будущее свободное время; правила для `COMPLETED` в прошедших датах описать явно и протестировать.

**FR-034.** Отмена записи сохраняет историю и освобождает слот.

**FR-035.** Удаление записи — отдельное действие с подтверждением; отмена не равна удалению.

**FR-036.** Для прошедшей записи можно поставить «Выполнена» и сохранить фактическую цену, если она отличается от плановой.

**FR-037.** При переносе записи сохранять клиента и услугу; после подтверждения показывать новую дату и время.

**FR-038.** Все операции записи должны быть атомарными и не оставлять частично изменённых данных.

### 4.5. Рабочие часы и свободное время

**FR-039.** В настройках задавать рабочие дни недели и время начала/конца рабочего дня (по умолчанию, например, 09:00–18:00; пользователь может изменить).

**FR-040.** При выборе времени подсвечивать интервалы внутри рабочего дня и предупреждать о записи вне графика; по умолчанию разрешать её только после явного подтверждения (это не ошибка валидации).

**FR-041.** Предлагать доступные интервалы с шагом 15 минут, учитывая длительность выбранной услуги и активные записи.

**FR-042.** Не показывать как свободные интервалы, в которые услуга не помещается целиком.

**FR-043.** Для MVP перерывы можно реализовать как отдельные блокировки времени либо отложить с явно задокументированным ограничением. Не считать время перерыва свободным, если функция блокировки реализована.

### 4.6. Напоминания

**FR-044.** Настройка напоминания мастеру: выключено / за 15 минут / за 30 минут / за 1 час до начала.

**FR-045.** При создании, переносе, отмене и удалении записи корректно создавать/обновлять/отменять соответствующее уведомление.

**FR-046.** На Android 13+ запрашивать разрешение `POST_NOTIFICATIONS` только при включении напоминаний, с понятным объяснением.

**FR-047.** Учитывать ограничения фоновой работы Android. WorkManager не гарантирует уведомление с точностью до минуты: в MVP допускается приблизительное напоминание, что нужно явно указать в настройках. Если продукту потребуются строго точные уведомления, отдельно спроектировать AlarmManager, разрешения и политику платформы.

**FR-048.** Не выводить конфиденциальные сведения на экране блокировки без соответствующей настройки; по умолчанию использовать нейтральный текст уведомления.

### 4.7. Настройки и данные

**FR-049.** Настройки: рабочие дни/часы, интервал сетки, напоминания, валюта отображения, тема (системная/светлая/тёмная — по возможности).

**FR-050.** Для MVP приложение полностью офлайн; данные хранятся локально на устройстве.

**FR-051.** Реализовать ручной экспорт и импорт резервной копии в выбранный пользователем файл через Storage Access Framework. Формат — версионированный JSON с клиентами, услугами, записями и настройками; не экспортировать URI телефонных контактов и другие лишние сведения.

**FR-052.** Импорт обязан валидировать версию, структуру и ссылки между сущностями. До применения показывать предупреждение, что импорт заменит или объединит данные; для MVP выбрать **полное восстановление с заменой после явного подтверждения**, транзакционно, с защитой от частичного восстановления.

**FR-053.** При ошибке импорта не изменять текущие данные. Протестировать повреждённые, пустые, слишком большие и несовместимые файлы.

**FR-054.** Объяснить пользователю, что удаление приложения/очистка данных может удалить локальную базу. Предложить экспорт копии.

**FR-055.** Не отправлять персональные данные клиентов на сервер. Не включать персональные данные в логи, crash reports и debug output.

## 5. Экранная структура и UX

### Нижняя навигация
1. **Расписание** — текущий день, выбор даты, список записей, «+».
2. **Клиенты** — поиск, карточки, добавление из контактов.
3. **Услуги** — список услуг, длительность и цена.
4. **Настройки** — рабочее время, уведомления, резервная копия.

### Основные экраны
- `ScheduleScreen` — дневной список, календарный переключатель.
- `AppointmentEditorScreen` — создание/редактирование записи.
- `AppointmentDetailsScreen` — подробности, перенос, статус, отмена.
- `ClientsScreen` — список и поиск.
- `ClientEditorScreen` — создание/редактирование, импорт контакта.
- `ClientDetailsScreen` — карточка и история.
- `ServicesScreen` / `ServiceEditorScreen` — услуги.
- `SettingsScreen` — параметры и экспорт/импорт.

### UI-принципы
- Интерфейс на русском; даты `дд.мм.гггг`, время 24-часовое.
- Крупные нажимаемые области (не менее рекомендуемого Material размера), контрастные подписи.
- Понятные состояния: загрузка, пустой список, ошибка, сохранено, конфликт.
- Кнопка сохранения блокируется на время операции; защита от двойного нажатия.
- Подтверждение перед удалением и разрушительным импортом.
- Обработка системной кнопки «Назад»; предупреждение о несохранённых изменениях.
- Поддержка увеличенного шрифта, TalkBack и экранов небольшого размера.
- Material 3; визуальный стиль: спокойная светлая палитра, аккуратные карточки, минимум лишних действий.
- Не хранить выбранную дату/введённую форму только в Composable без сохранения состояния при повороте экрана и пересоздании Activity.

## 6. Модель данных

Использовать стабильные UUID в строковом виде или другой обоснованный уникальный ключ. Все ссылки обеспечиваются внешними ключами Room.

### `clients`
| Поле | Тип | Правило |
|---|---|---|
| id | String (UUID) | PK |
| name | String | обязательное, trim, не пустое |
| phone | String? | оригинальное отображаемое значение |
| normalizedPhone | String? | для поиска/проверки дублей; нормализация с учётом страны, без ложных предположений |
| notes | String? | необязательное |
| archived | Boolean | false по умолчанию |
| createdAt | Instant | обязательное |
| updatedAt | Instant | обязательное |

### `services`
| Поле | Тип | Правило |
|---|---|---|
| id | String | PK |
| name | String | обязательное |
| defaultDurationMinutes | Int | > 0 |
| defaultPriceMinor | Long? | >= 0; деньги в минимальных единицах валюты |
| currencyCode | String | ISO 4217, например RUB, если выбран пользователем |
| notes | String? | необязательное |
| archived | Boolean | false по умолчанию |
| createdAt / updatedAt | Instant | обязательное |

### `appointments`
| Поле | Тип | Правило |
|---|---|---|
| id | String | PK |
| clientId | String | FK → clients.id |
| serviceId | String | FK → services.id |
| startAt | Instant | момент начала |
| durationMinutes | Int | > 0 |
| priceMinor | Long? | >= 0 |
| currencyCode | String | валюта цены |
| status | Enum/String | PLANNED/COMPLETED/CANCELLED/NO_SHOW |
| notes | String? | необязательное |
| serviceNameSnapshot | String | имя услуги на момент записи |
| clientNameSnapshot | String | имя клиента на момент записи, если нужно для экспорта/истории; не использовать вместо актуальной связи без причины |
| createdAt / updatedAt | Instant | обязательное |

**Пояснение:** хранить `startAt` как абсолютный момент времени, а календарные дни вычислять в выбранной локальной зоне. Настройка часового пояса: в MVP использовать системный часовой пояс устройства и явно описать поведение при его изменении; при необходимости хранить `ZoneId` рабочего места. Нельзя сравнивать даты через строковое форматирование. Записи через полночь либо поддержать корректно, либо явно запрещать с понятной валидацией; предпочтительно корректно поддержать, учитывая пересечения двух дней.

### `settings`
Использовать DataStore: рабочие дни, рабочие часы, шаг слотов, напоминания, валюта, тема. Для сложного расписания по дням можно хранить отдельную структуру с явной сериализацией и тестами.

### Индексы и ограничения
- Индекс `appointments(startAt)`.
- Индексы `appointments(clientId, startAt)` и `appointments(status, startAt)`.
- Индекс `clients(normalizedPhone)` без требования уникальности.
- Индекс/поиск клиентов по имени (при необходимости FTS; не усложнять MVP преждевременно).
- Foreign keys включены; удаление клиента/услуги не должно каскадно уничтожать историю.
- Room schema export включён; миграции обязательны для последующих версий.

## 7. Бизнес-правила и алгоритмы

### Пересечение интервалов
Два интервала конфликтуют тогда и только тогда, когда:

```kotlin
existingStart < newEnd && newStart < existingEnd
```

Для проверки учитывать записи, пересекающие границу дня; не ограничивать запрос только записями с датой начала, равной выбранной дате. Проверку выполнять атомарно с сохранением, чтобы избежать гонок.

### Поиск свободного слота
1. Получить рабочие интервалы выбранного дня.
2. Вычесть интервалы активных записей и блокировок.
3. Сформировать кандидатов с шагом 15 минут.
4. Оставить только кандидаты, где `start + duration <= endFreeInterval`.
5. Отобразить отсортированный список.
6. Повторно проверить доступность при нажатии «Сохранить».

### Деньги
- Не использовать `Float`/`Double` для хранения денежных значений.
- Отображать цену с учётом выбранной валюты и правил форматирования.
- Не смешивать суммы в разных валютах в одном итоге.
- Не считать стоимость завершённой записью, пока статус не `COMPLETED` (для будущей аналитики).

### Контакты
- Выбирать контакт только по явному действию пользователя.
- Не сканировать всю телефонную книгу в фоне.
- После выбора извлечь доступные имя/телефон, закрыть cursor через `use`.
- Учитывать отсутствие телефона, несколько номеров, отсутствие разрешённого URI, `SecurityException`, удалённый контакт и отмену выбора.
- Не сохранять ссылку на контакт как единственный источник данных: после импорта клиент должен существовать автономно.

## 9. Сценарии использования и критерии приёмки

### AC-01: первый запуск
**Дано:** чистая установка. **Когда:** мастер открывает приложение. **Тогда:** видит сегодняшний день, понятное пустое состояние, может создать клиента, услугу и запись; базовые услуги доступны после явного первоначального заполнения.

### AC-02: создание клиента
**Когда:** введено имя «Анна», телефон и нажато «Сохранить». **Тогда:** клиент появляется в поиске и доступен для выбора при записи; после перезапуска данные сохранены.

### AC-03: импорт телефонного контакта
**Когда:** мастер нажимает «Из контактов», выбирает контакт. **Тогда:** форма заполняется доступными полями; мастер подтверждает сохранение. При отмене системного выбора данные не повреждаются и приложение не падает.

### AC-04: запись
**Когда:** выбран клиент, услуга «Женская стрижка», дата и 10:00. **Тогда:** создаётся запись на 60 минут, отображается 10:00–11:00, после перезапуска остаётся в расписании.

### AC-05: конфликт
**Дано:** запись 10:00–11:00. **Когда:** пытаются добавить 10:30–11:30. **Тогда:** сохранение блокируется и показывается конфликт. Запись 11:00–12:00 допустима.

### AC-06: перенос
**Дано:** запись на 10:00. **Когда:** её переносят на 14:00. **Тогда:** прежний слот освобождён, новый занят; данные клиента и услуги сохранены.

### AC-07: отмена
**Когда:** запись отменена. **Тогда:** она остаётся в истории со статусом «Отменена», но не блокирует новое бронирование этого времени.

### AC-08: история клиента
**Дано:** у клиента две завершённые записи и одна будущая. **Тогда:** карточка показывает все три с правильными статусами и датами.

### AC-09: офлайн
**Дано:** включён режим полёта. **Когда:** мастер создаёт клиента и запись. **Тогда:** операция проходит без сети, данные сохраняются.

### AC-10: резервная копия
**Когда:** мастер экспортирует данные, очищает тестовую базу и импортирует файл. **Тогда:** восстанавливаются все сущности, связи и настройки. Повреждённый файл не изменяет существующую базу.

### AC-11: смена даты и поворот экрана
**Когда:** мастер выбирает дату и начинает заполнять форму, затем поворачивает устройство. **Тогда:** выбранная дата и введённые поля не теряются.

### AC-12: уведомления
**Когда:** напоминания включены и разрешены. **Тогда:** запланированное уведомление создаётся; после отмены/переноса старое уведомление не должно приходить. При запрете разрешения приложение продолжает работать без уведомлений.

## 10. Тест-план

### Unit tests (обязательны)
- Валидация клиента, услуги, записи.
- Конфликты: пересечение, соприкосновение границ, полное вложение, отменённые записи, редактирование себя.
- Свободные слоты: пустой день, заполненный день, разные длительности, границы рабочего времени.
- Форматирование цены, даты и времени.
- Нормализация телефона: разные пробелы/символы, международные номера; отсутствие ложного совпадения при неизвестном коде страны.
- Статусы и переходы между ними.

### Integration tests
- Room CRUD, связи, архивирование, индексы, миграции.
- Реактивное обновление расписания после изменений.
- Транзакционная проверка конфликта и сохранение.
- Экспорт/импорт и откат при ошибке.

### UI tests
- Создание клиента вручную.
- Создание записи с выбором клиента и услуги.
- Переход по датам.
- Предупреждение о конфликте.
- Отмена и перенос записи.
- Поиск клиента.
- Корректное поведение при пустых списках и ошибках.

### Ручные проверки на Android
- Android 8/10/13/14/актуальная версия (эмуляторы либо доступные реальные устройства).
- Светлая и тёмная тема, большой шрифт, TalkBack.
- Портретная ориентация, поворот, сворачивание/восстановление.
- Системный выбор контактов с несколькими номерами и без номера.
- Разрешение уведомлений предоставлено/отклонено.
- Работа без интернета, перезапуск, восстановление из копии.

## 11. Безопасность и приватность

1. Собирать только данные, которые мастер сам вводит или выбирает из системных контактов.
2. Не требовать доступ ко всей телефонной книге, если достаточно picker.
3. Не запрашивать интернет-разрешение, если оно не требуется для MVP.
4. Не писать имена, телефоны и заметки клиентов в логи.
5. Не использовать открытый внешний каталог для базы данных.
6. Экспортированный JSON **не зашифрован** в MVP: перед экспортом предупредить, что файл содержит персональные данные; предложить сохранять его в защищённом месте. Шифрованный экспорт — отдельная следующая задача.
7. Учесть применимые правила защиты персональных данных (в том числе GDPR, если приложение используется в ЕС); техническая реализация не заменяет юридическую оценку оснований обработки, сроков хранения и информирования клиентов.
8. Android Auto Backup: явно определить политику. Для MVP с персональными данными предпочтительно исключить базу из автоматического облачного резервирования до отдельного решения, задокументировав последствия; ручной экспорт остаётся доступен.
9. Удаление/архивирование должно быть предсказуемым; не допускать случайной потери истории.

## 12. Нефункциональные требования

- **Производительность:** открытие списка дня и поиск клиентов должны оставаться отзывчивыми при 5 000 клиентах и 20 000 записях на типичном устройстве среднего класса. Измерить, а не обещать без тестов.
- **Надёжность:** операции записи в БД транзакционные; UI не блокируется на IO.
- **Доступность:** TalkBack, достаточный контраст, масштабирование текста.
- **Локализация:** весь пользовательский текст вынести в Android string resources; первая локаль — `ru`.
- **Сопровождаемость:** понятные имена, небольшие функции, отсутствие ненужных абстракций.
- **Совместимость:** edge-to-edge и системная навигация на актуальных Android.
- **Сборка:** проект должен открываться в Android Studio и собираться командой Gradle.
- **Документация:** инструкции для новичка, который хочет установить приложение на свой Android.

## 14. Definition of Done

Работа считается завершённой только если:

- [ ] Приложение действительно запускается на Android.
- [ ] Создание/редактирование/архивирование клиентов работает.
- [ ] Импорт выбранного контакта работает без массового доступа к телефонной книге.
- [ ] Создание/редактирование/архивирование услуг работает.
- [ ] Записи создаются, отображаются по датам, переносятся и отменяются.
- [ ] Пересечения активных записей корректно блокируются.
- [ ] История клиента не теряется при редактировании клиента/услуги.
- [ ] Данные сохраняются офлайн и после перезапуска.
- [ ] Уведомления корректно обрабатывают разрешения и изменения записей.
- [ ] Экспорт/импорт работают, ошибочный импорт не портит БД.
- [ ] Основные unit/integration/UI tests реализованы и выполнены, если доступна среда.
- [ ] `./gradlew assembleDebug` завершается успешно в доступной среде.
- [ ] Подготовлена понятная инструкция установки APK.
- [ ] В README честно перечислены реализованные функции и ограничения.
- [ ] Нет заглушек в критических пользовательских сценариях, имитирующих сохранение.

## 17. Инструкция Codex: как начать работу

**Начинай реализацию сразу, а не ограничивайся пересказом ТЗ.**

1. Проверь текущий репозиторий и доступные инструменты.
2. Кратко сформулируй архитектуру и перечисли критические предположения.
3. Создай минимальный запускаемый Android-проект.
4. Реализуй **первый вертикальный срез**: Room → клиент → экран списка → форма добавления → сохранение → тест.
5. Затем реализуй услуги и полный сценарий создания записи.
6. После каждого среза запускай доступные проверки и исправляй ошибки.
7. Продолжай до выполнения MVP и критериев приёмки. Если ограничен контекстом или временем, оставь работоспособный проект и точный TODO, а не недописанные критические сценарии.

### Приоритеты при ограничении времени
1. Сохранение данных и корректность расписания.
2. Добавление клиента, включая системный выбор контакта.
3. Создание/перенос/отмена записи и проверка конфликтов.
4. Удобство календаря и поиск клиентов.
5. Резервное копирование.
6. Уведомления и визуальные улучшения.

**Запрещено:** объявлять MVP готовым, если основные кнопки только показывают демонстрационные сообщения или данные исчезают после перезапуска.

## 18. Решения, требующие подтверждения владельца продукта перед публикацией

- Название приложения и иконка.
